## Part 1 — what happened

### Phase 1 — orientation and skills import (PR #1)

Goal: get oriented and copy the `self-retrospective` skill in from the owner's software-factory repository. The repo held only a charter, a 39-scenario brainstorm, and a LICENSE. The copy hit a wall of access denials: GitHub MCP (session scope), `add_repo` (declined by the owner — the repo is public), then `api.github.com`, `codeload`, and `github.com` HTML all intercepted by the session proxy. Only `raw.githubusercontent.com` served content, and with no directory listing the skill's files had to be enumerated by grepping SKILL.md for path references. That method silently missed `spec/SPEC.md` — discovered one PR later while probing for the `adr` skill's files, and back-filled. Two more skills (`adr`, `human-scoped-deliverables`) were imported the same way, plus a README, and the owner had the PR merged.

### Phase 2 — design discussion (no commits; the doctrine)

The owner set the mission (wave-1 scenarios against the published docs site) and predicted the agent would "immediately hit things where you are making assumptions." Confirmed before any scenario work: the agent had repeated the brainstorm's claim that scenario S1 was "already at L4," which the owner rejected — no rebuild documentation exists, so by the corpus's own maturity definitions S1 cannot be past L0. The contamination rode in through an *allowed* source (the charter's own parenthetical), which sharpened the methodology. The owner then laid down the doctrine that shaped everything after: deterministic enforcement over prose rules ("CLAUDE.md rules are not worth the electrons"), JSON-over-Markdown for anything linted, jq-only mutation, ADRs that are checked rather than shelved, assumptions tracked centrally with scoping, findings pulled by consumers rather than pushed, and docs-blind authoring implemented as physically isolated subagents. Scope decisions: one depth probe (S4) instead of a breadth sweep; author scenarios deferred.

### Phase 3 — the ledger (PR #2, first commit)

The owner's standing loss — "excellent ideas during discussion in agent sessions" evaporating unpreserved — became TODO.json: thirty items, stable append-only T-NNN IDs, phases A–D as explicit proposals, dependencies, and handoff-quality summaries. Deliberately a committed canonical-JSON artifact rather than session-local task state.

### Phase 4 — jq mechanics, dogfooded (T-006/T-007)

Built `scripts/lint-json` (well-formedness, `jq -S` canonical round-trip, JSON Schema validation via `schemas/map.json`, semantic checks), `scripts/jq-edit` (atomic filter-mutate-lint), `scripts/validate-schema.py`, the TODO schema, and the `canonical-json-editing` skill. The tooling immediately convicted its own author twice: the linter's first full run caught unsorted tag arrays in the hand-written TODO.json, and the first real `jq-edit` call put `--arg` before the filter — an error also found baked into a just-written skill recipe. Both fixed via the tools themselves; both are exactly the argument for deterministic enforcement.

### Phase 5 — the boundary and the experiments tier (T-002/T-003)

Wrote the docs-blindness PreToolUse hook (deny any tool-call text referencing the platform source; scrub this repo's own `-scenarios` name first; fail closed; 19 table-driven tests) and wired it via `.claude/settings.json`. It took effect mid-session and denied its author's very next Bash call — the ledger-update text being passed as a jq `--arg` spelled out the forbidden path. Prose was reworded; the commit message written obliquely; the trade-off (conservative text-scan, occasional wording contortions) accepted and documented. `experiments/` landed as the loose tier: well-formedness-only linting, throwaway expectation stated in its README. PR #2 merged.

### Phase 6 — handoff

Wrote the S4 probe launch prompt for a fresh session: verbatim scenario bullet, docs-root-only inputs, loose JSON output shape, stop-for-review after reporting. Ledger updated throughout via `jq-edit`; check-in triggers armed while PRs were open and deleted at merge.

## Part 3 — agents-file suggestions

Proposed additions to the project's agents file (`AGENTS.md`). Each rule has its own per-rule file in the sibling directory — `# agent instruction` is what a CI/CD assembler concatenates into `AGENTS.md`; `# justification` is for reviewers and is stripped by the assembler. Both are mirrored inline here for review-decision convenience.

### Suggestion 1: Keep the platform-source path out of tool-call text — `AGENTS-MD-5120e01835`

- **Per-rule file**: [./2026-07-06-2/AGENTS-MD-5120e01835-keep-platform-source-path-out-of-tool-call-text.md](./2026-07-06-2/AGENTS-MD-5120e01835-keep-platform-source-path-out-of-tool-call-text.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Keep the platform-source path out of tool-call text.** The docs-blindness hook scans the full text of Bash commands and other tool inputs. Never write the platform source repository's owner/repo path into a shell command, a commit message, or prose passed through a command argument — refer to it obliquely ("the platform source repository") instead. Content at rest in files is not scanned; only tool-call text is.
>
> *Grounded in: the hook denying its own author's next Bash call minutes after installation.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Within one minute of `.claude/settings.json` being written, the hook denied the very next Bash call — a `jq-edit` invocation whose `--arg` string described the hook and spelled out the forbidden path. The whole three-command chain died at PreToolUse, costing a full rewrite of the ledger-update text and a re-run; the subsequent commit message had to be reworded the same way. The failure mode recurs every time an agent writes *about* the boundary (ledger notes, commit messages, README prose piped through a command), which in a scenario-testing repository is constantly. The marginal cost of the rule is one oblique phrase instead of a literal path; the cost of not knowing it is a denied call and a confused retry loop every session, or — worse — an agent "fixing" the denial by weakening the hook.

### Suggestion 2: Mutate canonical JSON only via jq-edit — `AGENTS-MD-4f3a50e00b`

- **Per-rule file**: [./2026-07-06-2/AGENTS-MD-4f3a50e00b-mutate-canonical-json-only-via-jq-edit.md](./2026-07-06-2/AGENTS-MD-4f3a50e00b-mutate-canonical-json-only-via-jq-edit.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Mutate canonical JSON only via jq-edit.** Never text-edit a tracked .json file (no Edit/Write tools, no sed/awk). Use scripts/jq-edit FILE FILTER [JQ_ARGS...] — the filter is always the second argument, and options like --arg come after it — and run scripts/lint-json before every commit.
>
> *Grounded in: the tool's author violating its argument order minutes after writing it, plus the identical error in a just-written skill recipe.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The author of `scripts/jq-edit` put `--arg` before the filter on the first real call after writing the tool — jq failed, the wrapper correctly left the file unchanged, and investigating the failure revealed the same wrong order baked into a recipe in the freshly written `canonical-json-editing` skill. Two violations of a convention by its own author, inside ten minutes, is the whole argument for deterministic enforcement in one anecdote: humans and agents will not hold argument order in their heads, so the wrapper (atomic replace + auto-lint) and the pre-commit lint have to. Cost of the rule: none — `jq-edit` is already the shorter path. Cost without it: malformed JSON, trailing commas, and diffs that lie, each requiring recovery-by-hand in a repo whose premise is that machine-owned records stay machine-parseable.

### Suggestion 3: Bootstrap new JSON files through immediate canonicalization — `AGENTS-MD-f6a1a629a1`

- **Per-rule file**: [./2026-07-06-2/AGENTS-MD-f6a1a629a1-bootstrap-new-json-files-through-immediate-canonicalization.md](./2026-07-06-2/AGENTS-MD-f6a1a629a1-bootstrap-new-json-files-through-immediate-canonicalization.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Bootstrap new JSON files through immediate canonicalization.** Creating a JSON document with the Write tool is acceptable exactly once, at birth; immediately canonicalize and lint it with scripts/jq-edit FILE '.' before doing anything else. All subsequent mutations go through jq-edit.
>
> *Grounded in: schemas/todo.schema.json, schemas/map.json, and .claude/settings.json all bootstrapped this way this session.*

**Justification** (verbatim from the per-rule file's `# justification` section):

There is no jq path to create a file from nothing, so a bootstrap exception exists — but it must close instantly. The first hand-written TODO.json carried unsorted tag arrays that violated the repository's own declared convention; the linter caught it only because canonicalization ran right after creation. All three later files (the schema, the schema map, the hook settings) were written then immediately passed through `scripts/jq-edit FILE '.'`, which sorted keys, normalized indentation, and ran the linter in one step — a five-second habit. Without the habit, hand-authored files drift from canonical form at birth, the first later mutation produces a diff mixing real changes with mass reformatting, and review signal drowns in noise.

### Suggestion 4: Probe conventional subdirectories when mirroring a skill — `AGENTS-MD-33bf44ea86`

- **Per-rule file**: [./2026-07-06-2/AGENTS-MD-33bf44ea86-probe-conventional-subdirectories-when-mirroring-a-skill.md](./2026-07-06-2/AGENTS-MD-33bf44ea86-probe-conventional-subdirectories-when-mirroring-a-skill.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Probe conventional subdirectories when mirroring a skill.** When copying a skill (or similar directory) from a repository whose directories you cannot list, do not rely solely on scanning SKILL.md for referenced paths — also probe the conventional subdirectories (resources/, scripts/, templates/, spec/, references/, assets/, examples/) for standard files. Reference-scanning alone misses files nothing links to.
>
> *Grounded in: the self-retrospective skill's spec/SPEC.md missed on first copy, recovered by a later probe.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The first import of the self-retrospective skill enumerated files by grepping SKILL.md for `resources/`, `scripts/`, and similar path references — and shipped an incomplete mirror: the skill's `spec/SPEC.md` (48 KB, the implementation-grade spec) was referenced only obliquely and the grep pattern didn't include `spec/`. The gap was found one PR later, by accident, while probing for a *different* skill's files. The fix costs one loop of HEAD-style probes against a handful of conventional names (a missing file returns a detectable sentinel); the failure costs an incomplete artifact that looks complete — the worst kind, because nothing fails until someone needs the missing file in a session that can no longer reach the source.

### Suggestion 5: Fetch out-of-scope public repos via raw.githubusercontent.com — `AGENTS-MD-fd414c21c9`

- **Per-rule file**: [./2026-07-06-2/AGENTS-MD-fd414c21c9-fetch-out-of-scope-public-repos-via-raw-githubusercontent.md](./2026-07-06-2/AGENTS-MD-fd414c21c9-fetch-out-of-scope-public-repos-via-raw-githubusercontent.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Fetch out-of-scope public repos via raw.githubusercontent.com.** For public GitHub repositories outside the session's repository scope, github.com, api.github.com, and codeload.github.com are proxy-intercepted and return a JSON error body; raw.githubusercontent.com serves file content. A missing file returns the literal body "404: Not Found" with curl exit 0 — check for that sentinel explicitly.
>
> *Grounded in: importing three skills from a sibling public repository through the proxy.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Importing the first skill burned four failed attempts before finding the working path: the GitHub MCP tool was denied by session scope, `add_repo` was denied by the user (the repo is public — session integration was unnecessary), then `api.github.com`, `codeload.github.com`, and the `github.com` HTML tree page each returned the proxy's JSON interception message. Only `raw.githubusercontent.com` served content. A second trap followed: probing for optional files "succeeded" with a 200-looking curl that actually delivered the fourteen-byte body `404: Not Found`, which would have been silently saved as a file. Both facts cost real time to discover and are invisible in any documentation; encoding them saves every future import the same archaeology. Marginal cost: one URL habit and one string comparison.

### Suggestion 6: TODO.json is the handoff — read it first, update it as you land work — `AGENTS-MD-b54f8bb12e`

- **Per-rule file**: [./2026-07-06-2/AGENTS-MD-b54f8bb12e-todo-json-is-the-handoff.md](./2026-07-06-2/AGENTS-MD-b54f8bb12e-todo-json-is-the-handoff.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **TODO.json is the handoff — read it first, update it as you land work.** At session start in this repository, read TODO.json before planning. When work lands, update item statuses via scripts/jq-edit in the same PR (append a delivery note to the item's summary); when new ideas surface in discussion, append them as new T-NNN items rather than letting them evaporate with the session.
>
> *Grounded in: the ledger's founding purpose — the owner losing good ideas from earlier agent sessions.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The owner created the ledger after watching, in his words, "excellent ideas during discussion in agent sessions" get lost "over and over again" because nothing preserved them past context truncation. This session then demonstrated the intended loop end-to-end: thirty items captured from one design discussion, four of them implemented within hours with statuses flipped and delivery notes appended in the same PRs, and the S4 probe launch prompt for the next session written *against ledger item IDs* rather than against conversation memory. The rule's cost is one file read at session start and one jq-edit per landed item. Skipping it re-creates the exact failure the ledger exists to prevent — and leaves statuses lying, which is worse than no ledger because it manufactures false confidence about what is done.

### Suggestion 7: Clean up scheduled check-ins when their PR closes — `AGENTS-MD-d2782280eb`

- **Per-rule file**: [./2026-07-06-2/AGENTS-MD-d2782280eb-clean-up-scheduled-check-ins-when-their-pr-closes.md](./2026-07-06-2/AGENTS-MD-d2782280eb-clean-up-scheduled-check-ins-when-their-pr-closes.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Clean up scheduled check-ins when their PR closes.** If you armed a send_later self check-in to watch a pull request, delete the trigger the moment the PR merges or closes. Orphaned triggers fire into finished work and waste a wake-up on nothing.
>
> *Grounded in: deleting the armed check-in triggers after PR #1 and PR #2 merged.*

**Justification** (verbatim from the per-rule file's `# justification` section):

Both PRs in this session had hourly self check-ins armed (webhooks do not deliver CI success or merge transitions, so the check-ins are necessary while a PR is open). Both were deleted at merge time — the second one seconds after the merge call returned. The first deletion attempt hit a transient tool failure and had to be retried after an MCP reconnect, which is exactly why the rule needs stating: the cleanup is easy to drop when it errors once, and an orphaned trigger then fires into a merged PR, wakes a session with no work to do, and — if the firing session lacks context — can generate a confused status message to the owner. Cost of the rule: one delete_trigger call per merged PR. Cost without it: a phantom wake-up per orphan per hour.

### Suggestion 8: Founding-document claims about platform state are not evidence — `AGENTS-MD-444d074d39`

- **Per-rule file**: [./2026-07-06-2/AGENTS-MD-444d074d39-founding-document-claims-are-not-evidence.md](./2026-07-06-2/AGENTS-MD-444d074d39-founding-document-claims-are-not-evidence.md)

**Proposed agent instruction** (verbatim from the per-rule file's `# agent instruction` section):

> **Founding-document claims about platform state are not evidence.** The charter and brainstorm may assert platform facts (for example, a scenario "already at L4"). Do not propagate such claims into scenario or ledger records unless they are verifiable from the published documentation; an unverifiable claim is finding material, not fact.
>
> *Grounded in: the owner rejecting the founding claim that the rebuild scenario was already at L4 — no rebuild documentation exists.*

**Justification** (verbatim from the per-rule file's `# justification` section):

The brainstorm document states that scenario S1 (rebuild the platform from nothing) is "already at L4 — this is the existing clean-build loop." The agent repeated that claim in a design recommendation; the owner rejected it flatly: as a user, he has no documented way to rebuild, no owner-facing status surface, no remediation story — so by the corpus's own maturity definitions the scenario cannot be past L0, and the founding claim itself is a likely documentation bug. The subtlety that makes this rule necessary: the charter is an *allowed source* under the docs-blindness contract, so nothing mechanical stops the contamination — the claim rode in through a legitimate channel. The rule costs one verification question per inherited claim ("which docs page supports this?"). Without it, the corpus's baseline data is polluted by the very repository that defines its rules.
